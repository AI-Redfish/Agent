## 一句话总结

A2A（Agent-to-Agent）协议是一套让不同 Agent 之间进行**能力发现、任务协商与跨 Agent 通信**的开放协作规范；它不是某个具体框架，而是约定 Agent 如何暴露能力、声明依赖、接收任务并返回结果。

## 背景：为什么需要 A2A

随着 AI Agent 从通用助手走向大量垂直场景，越来越多私有 Agent 会按照业务职责拆分：

- 客服 Agent：负责回答用户问题。
- 库存 Agent：负责查询库存。
- 物流 Agent：负责调度配送。
- 订单 Agent：负责管理订单状态。

这些 Agent 的业务逻辑、数据来源和能力边界不同。一个 Agent 在执行任务时，常常需要调用另一个 Agent 的能力，例如：

- 客服 Agent 被问到“现在有没有库存”，但它自身没有查库存能力，需要调用库存 Agent。
- 物流 Agent 做配送调度时，需要了解订单状态，否则可能产生数据偏差。

因此，需要一种机制让 Agent 之间能够：

1. 发现对方有什么能力。
2. 判断哪些能力可以被调用。
3. 按统一规则发起请求、传递任务、返回结果。

A2A 协议就是为了解决这些问题而提出的 Agent 间协作规范。

## A2A 要解决的三个核心问题

### 1. 服务发现

调用方如何知道另一个 Agent：

- 在哪里；
- 能做什么；
- 暴露了哪些能力；
- 需要什么输入；
- 会返回什么输出。

### 2. 任务协商

Agent 之间不能随意互调，需要有明确规约：

- 当前 Agent 是否允许调用目标 Agent；
- 可以调用目标 Agent 的哪些能力；
- 一次任务如何标识与追踪；
- 输入输出格式如何约束。

### 3. 跨 Agent 通信

当一个任务跨多个 Agent 传递时，需要统一通信方式：

- 请求发到哪里；
- 用什么字段说明要调用的能力；
- 如何传递任务 ID；
- 如何返回状态与结果。

## 核心设计：两个固定端点

视频中强调，A2A 的核心不是某个语言或框架，而是每个 Agent 遵循相同的暴露方式。一个支持 A2A 的 Agent 通常需要暴露两个端点。

### 1. `agent.json`

`agent.json` 用来暴露 Agent 的能力描述，也可以理解为该 Agent 的“智能体卡片”（Agent Card）。

它主要描述：

- Agent 的基础元数据；
- Agent 的访问 URL；
- Agent 能提供哪些技能（Skill）；
- 每个 Skill 的名称、描述、输入参数、输出格式；
- 当前 Agent 依赖哪些其他 Agent；
- 依赖 Agent 中允许调用哪些 Skill。

通过读取 `agent.json`，调用方可以知道目标 Agent 能做什么、怎么调用、调用后会返回什么。

### 2. `a2a/task`

`a2a/task` 是统一任务调用入口。

无论要调用 Agent 的哪个动作或能力，都向这个任务端点发送请求。请求中通过 Skill 等字段指定要执行的具体能力。

可以理解为：

- `agent.json` 负责“能力发现”；
- `a2a/task` 负责“任务执行”。

## Agent Card：能力声明

Agent Card 是 `agent.json` 返回的核心内容。

它类似服务说明书，告诉外部调用方：

- 我是谁；
- 我的服务地址是什么；
- 我支持哪些能力；
- 每个能力怎么调用；
- 输入字段有哪些；
- 哪些字段是必填；
- 输出结构是什么；
- 我依赖哪些下游 Agent。

视频中以“旅游建议 Agent”为例：

- 旅游建议 Agent 提供 `TravelAdvice` 一类的能力。
- 输入可能包含城市、出行日期等参数。
- 输出可能是旅游建议结果。
- 因为旅游建议依赖天气信息，所以它还声明了对天气 Agent 的依赖。

## Skill：能力单元

Skill 是 Agent 对外提供的一个具体能力单元。

可以类比传统后端开发中的：

- Controller 中的一个接口；
- Service 中的一个业务方法；
- 一项可被外部调用的动作。

每个 Skill 通常包含：

- 名称；
- 描述；
- 输入参数结构；
- 必填字段；
- 输出结构。

一个 Agent 可以暴露多个 Skill，但调用方不一定能调用全部能力。通过依赖声明和权限约定，可以限制上游 Agent 只能调用特定 Skill。

## Dependencies：依赖声明

`dependencies` 用来声明当前 Agent 依赖哪些其他 Agent，以及可以调用对方的哪些能力。

它的作用类似服务注册或依赖清单：

- 声明下游 Agent 的 URL；
- 声明需要使用下游 Agent 的哪些 Skill；
- 限制当前 Agent 不能随意调用下游 Agent 的其他能力。

这也是一种安全约束：

- 旅游 Agent 只需要天气 Agent 的天气查询能力；
- 那么它就只声明并调用天气查询 Skill；
- 不应该拥有调用天气 Agent 其他能力的权限。

## Task：一次完整交互

Task 代表一次完整的 Agent 调用链路。

一次任务可能跨多个 Agent：

1. 客户端调用旅游 Agent；
2. 旅游 Agent 为完成任务调用天气 Agent；
3. 天气 Agent 返回天气信息；
4. 旅游 Agent 结合自己的业务逻辑生成旅游建议；
5. 旅游 Agent 将最终结果返回客户端。

在这个过程中，Task ID 用来标识并串联一次完整交互，便于在多个 Agent 之间传递和追踪。

Task 请求通常包含：

- 唯一任务标识；
- 要调用的 Skill；
- 输入内容。

Task 响应通常包含：

- Task ID；
- 任务状态；
- Agent 返回的具体结果。

## 示例流程：旅游 Agent 调用天气 Agent

### 第一步：客户端读取旅游 Agent 的 `agent.json`

客户端先访问旅游 Agent 的 `agent.json`，获取：

- Agent 名称；
- 版本；
- 描述；
- 支持的 Skill；
- 输入输出格式；
- 对天气 Agent 的依赖声明。

### 第二步：客户端调用旅游 Agent 的 `a2a/task`

客户端向旅游 Agent 的 `a2a/task` 发起请求：

- 传入 Task ID；
- 指定 Skill，例如旅游建议；
- 传入用户输入，例如城市“北京”和出行日期。

### 第三步：旅游 Agent 发现并调用天气 Agent

旅游 Agent 为生成旅游建议，需要天气信息，于是：

1. 访问天气 Agent 的 `agent.json`；
2. 确认天气 Agent 暴露了天气查询 Skill；
3. 向天气 Agent 的 `a2a/task` 发起天气查询请求。

### 第四步：天气 Agent 返回结果

天气 Agent 根据输入城市返回天气情况。

### 第五步：旅游 Agent 生成最终结果

旅游 Agent 将天气结果与自身旅游建议逻辑结合，生成最终旅游建议，并返回给客户端。

## A2A 的本质

A2A 并不是一个复杂的新技术，而是一套通信协议和开发约定。

它通过两个关键端点完成 Agent 协作：

- `agent.json`：发现能力、声明 Skill、声明依赖；
- `a2a/task`：发起任务、传递输入、返回状态和结果。

只要不同 Agent 遵循同一套规则，就可以实现跨 Agent 的能力发现、任务调用和结果传递。

## 落地实现

视频中提到，A2A 落地时不同语言会有自己的开发方式。

目前以 Google 主导的 A2A 生态为主，Python 和 TypeScript/JavaScript 方向都开始出现相关 SDK 或框架支持。实际开发时，可以借助这些 SDK 自动生成 Agent Card、维护端点与数据结构，避免手写协议细节导致代码和能力声明不一致。

## 关键启发

- 垂直 Agent 越多，Agent 间协作越重要。
- A2A 的重点是标准化 Agent 之间的“发现—调用—返回”流程。
- `agent.json` 类似服务说明书，`a2a/task` 类似统一任务入口。
- Skill 是 Agent 的最小可调用能力单元。
- Dependencies 不只是依赖清单，也是一种调用范围和安全边界。
- Task ID 让一次跨 Agent 调用链路可以被追踪。
- A2A 更像协议规范，而不是绑定某个具体框架或语言。
