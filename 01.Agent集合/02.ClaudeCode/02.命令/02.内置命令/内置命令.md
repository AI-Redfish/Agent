## /context

看当前会话的 token 用量，看哪些内容在占上下文：系统提示、历史消息、技能、记忆文件、代理等。



**使用场景**

- 判断为什么它开始“忘事”或跑偏；
- 判断为什么会话变慢；
- 查看还剩多少上下文可用。
- 项目规则很多，想确认是不是某个 CLAUDE.md 或技能在影响行为、
- 想决定要不要新开会话



**使用**

```
/context
```



 **内容说明**
  - System prompt：系统级规则和环境说明。
  - Messages：你和 Claude 的历史对话，通常占比最大。
  - Custom agents：调用过或加载过的代理相关上下文。
  - Skills：已加载技能的说明内容。
  - Memory files：像 CLAUDE.md 这类自动注入的项目规则文件。
  - Autocompact buffer：为自动压缩上下文预留的缓冲空间。
  - Suggestions：针对当前会话的优化建议，比如“少读整文件，多用 offset/limit”。





**优化建议**

  - 少贴整段大日志/大文件，尽量只贴关键片段。
  - 读取文件时用 offset / limit，不要反复全量读。
  - 大任务分阶段做，必要时新开会话。
  - 稳定规则写进 CLAUDE.md，不要每次重复说。
  - 如果 Messages 占比特别高，说明历史对话太长了，适合收束或开新会话。

## /rewind

当你输入 `/rewind` 或连按两次 `Esc` 键后，会弹出一个历史节点列表。选择一个节点后，你可以进行以下几种精细化的回退操作：



**回退代码和对话 (Restore code and conversation)**

**作用**：这是传统的“撤销”功能。它会将你的代码文件和对话上下文都恢复到选定的时间点，就像什么都没发生过一样。

**场景**：Claude 进行了一系列修改，结果完全跑偏了，你想彻底回到修改前的状态。



**仅回退代码 (Restore code only)**

**作用**：这是 `/rewind` 的“杀手锏”功能。它会撤销代码的所有更改，但**保留对话历史**。

**场景**：你让 Claude 尝试了一种实现方案，但效果不好。使用这个功能，代码会复原，但 Claude 依然“记得”你们尝试过这种方法并且失败

了。这样你就可以直接告诉它：“刚才那种方法不行，我们换个思路试试”，而无需重新解释需求。



**仅回退对话 (Restore conversation only)**

**作用**：撤销对话历史，但**保留当前代码的所有更改**。

**场景**：你对代码的修改结果很满意，但觉得中间的讨论过程太混乱，或者想收回某个错误的指令，让对话从一个更清晰的节点重新开始。



**从该点压缩对话 (Summarize from here)**

**作用**：压缩从选定节点开始的对话内容，以释放上下文窗口空间。

**场景**：在一个非常长的会话中，早期的讨论已经不再重要，通过压缩来节省 Token，让 Claude 能更专注于当前的任务。

# 自动化与目标执行

## /goal

设置当前会话的“完成条件”。每轮结束后自动判断目标是否满足。未满足时继续下一轮，不需要反复手动输入“继续”。

满足后自动清除当前 goal。



它适合有明确验收标准的大任务，例如迁移 API、修复测试、完成某个功能、清理遗留调用、批量重构等。



**底层设计模式**

`/goal` 本质上是一个会话级的目标控制器，底层是 Actor-Evaluator Loop。

- 主模型负责执行任务。
- 评估模型负责判断目标是否满足。
- 每轮结束时触发一次检查。
- 如果目标未满足，评估结果会反馈给主模型继续下一轮。
- 如果目标满足，会清除 goal 并停止。

可以理解为：

```
设置目标 -> 主模型执行 -> 评估器验收 -> 未完成则继续 / 已完成则停止
```

它不是让模型一次性完成所有事，而是把任务拆成多轮执行，并用独立评估器在每轮之间判断是否继续。



**使用**

```
/goal <完成条件>
```

示例：

```
/goal 修复 checkout 流程，直到 npm test 和 npm run build 都通过。
```

更推荐写成可验证目标：

```
/goal 迁移所有 oldAuthClient 调用到 newAuthClient；用 rg "oldAuthClient" src 无匹配、npm test 通过来证明完成；不要修改测试文件。
```

查看当前目标：

```
/goal
```

清除当前目标：

```
/goal clear
```

**写法建议**

- 写清楚最终状态，不要只写“优化一下”。
- 写清楚验证方式，比如测试、构建、搜索结果。
- 写清楚约束，比如不改测试、不引入新依赖、不改公共 API。
- 长任务最好加停止条件，比如“如果 12 轮后仍阻塞，输出剩余问题”。



**适用边界**

- 适合可验证的工程任务。
- 不适合开放式探索或目标模糊的问题。
- 评估器不会自己运行命令，只会根据 Claude 已经展示的结果判断，所以要让 Claude 明确执行并汇报验证命令。

基本用法：

  - 输入 /debug 问题描述：带着具体问题排查，例如 /debug 发送消息后卡住。
  - 如果问题发生在 Claude Code 启动阶段：用 claude --debug 重新启动，这样能捕获启动日志。
