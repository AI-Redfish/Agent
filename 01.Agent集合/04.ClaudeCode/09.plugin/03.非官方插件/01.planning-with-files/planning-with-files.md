# 概述

`planning-with-files` 是一个为 Claude Code 提供“文件式持久化规划”的插件。

它的核心目标是把复杂任务中的**计划、发现、进度**落到项目文件里，让 Claude 在以下场景下仍然能快

速恢复上下文：

- 长任务导致上下文变长
- 执行 `/clear` 后重新开始
- 关闭会话后第二天继续
- 多轮排障时避免重复试错

可以把它理解成：把原本只存在于上下文里的临时记忆，转成存放在项目中的 Markdown 文件。



**适用场景**

从文章给出的案例来看，这个插件尤其适合以下任务：

1. 研究型任务

例如：调研“微服务架构的优缺点”、比较技术方案、梳理最佳实践。

这类任务需要反复搜索、阅读、整理，`findings.md` 非常有价值。

2. Bug 修复任务

例如：定位一个 `TypeError`、追踪异步调用链、逐步缩小问题范围。

这类任务容易反复试错，把错误写入 `task_plan.md` 能显著减少重复劳动。

3. 多阶段功能开发

例如：先调研、再设计、再实现、最后测试。

这类任务天然适合拆成阶段，并用复选框跟踪进度。

4. 跨会话长任务

如果一个任务不可能在一个会话里做完，或者中间需要多次中断，再恢复时文件式计划会非常有帮助。

# 三文件模式

## `task_plan.md`

这是“指挥中心”，负责记录任务本身。

通常包含：

- 任务目标
- 分阶段计划
- 当前所处阶段
- 遇到的错误与处理方式
- 当前状态说明

示例结构：

```markdown
# task_plan.md

## 目标
重构用户认证模块，支持 OAuth2.0。

## 阶段
- [x] 阶段 1: 调研现有认证代码 ✓
- [x] 阶段 2: 设计新的认证架构 ✓
- [ ] 阶段 3: 实现 OAuth2.0 流程（当前）
- [ ] 阶段 4: 迁移现有用户
- [ ] 阶段 5: 测试和上线

## 状态
**当前在阶段 3** - 正在实现授权码流程

## 遇到的错误
- Error: redirect_uri_mismatch
  → 原因：配置文件里的回调地址和注册的不一致
  → 解决：更新 OAuth 配置
```

##  `findings.md`

这是“知识库”，负责记录研究和分析结果。

通常包含：

- 代码库结构
- API / 配置 /依赖的使用方式
- 关键发现
- 踩坑记录
- 技术决策及原因

示例结构：

```markdown
# findings.md

## 代码库结构
- `/auth` - 认证相关代码
- `/middleware` - 认证中间件
- `/models/user.js` - 用户模型

## 关键发现
1. 现有系统使用 session 认证，不支持 token
2. 用户密码用 bcrypt 加密，可以直接迁移
3. 数据库有 unique 约束在 email 字段

## 技术决策
| 决策 | 理由 |
|------|------|
| 使用 passport.js | 社区成熟，OAuth 支持完善 |
| 保留 session 兼容 | 老用户平滑迁移 |
```

## `progress.md`

这是“工作日志”，负责记录实际执行过程。

通常包含：

- 做了哪些操作
- 修改了哪些文件
- 执行了哪些命令
- 测试结果怎样
- 每个时间点推进到了哪里

示例结构：

```markdown
# progress.md

## 2024-02-24 会话记录

### 10:30 - 开始实现 OAuth 流程
- 创建了 `/auth/oauth.js`
- 添加了 passport-google-oauth20 依赖
- 测试：/auth/google 跳转正常

### 11:15 - 遇到 redirect_uri 错误
- 错误：redirect_uri_mismatch
- 排查：发现配置文件写的是 localhost:3000
- 修复：改成 localhost:8080
- 测试：问题解决

### 14:00 - 完成授权码流程
- 实现了完整的 OAuth2.0 授权码流程
- 测试用例通过
```



# 工作流程

文章中总结的典型工作流可以概括为 5 步：



**第一步：先创建计划**

遇到复杂任务时，第一件事不是直接写代码，而是先创建 `task_plan.md`。

插件会把“先有计划再执行”作为前置条件；没有计划文件时，不应直接进入后续复杂操作。



**第二步：进入执行循环**

任务开始推进后，Claude 不再只依赖当前上下文，而是围绕计划文件反复工作。

尤其是在关键操作前，插件会通过钩子重新读取计划，避免任务跑偏。



**第三步：遵守“2 次操作后更新 findings”规则**

- 操作 1：`WebSearch` 搜索资料 
- 操作 2：`WebFetch` 获取文档 → **必须更新 `findings.md`**
- 操作 3：读取代码文件 → 记录发现
- 操作 4：`Grep` 搜索关键字 → **必须更新 `findings.md`**

这个规则的意义是：**强制及时整理，而不是把信息堆到最后。**



**第四步：把错误写进计划文件**

遇到错误时，不只是修，还要把错误、原因、解决方案写入 `task_plan.md` 的“遇到的错误”部分。

这样后续继续任务时，可以直接复用历史排障结论，避免重复试错。



**第五步：结束前做完成度校验**

当 Claude 认为任务已经完成、准备停止时，插件会检查：

- 所有阶段是否都已完成
- 是否仍有未勾选的步骤
- 是否真的满足结束条件

如果计划中还有未完成项，插件会提醒继续推进。



**4 个关键钩子**

文章中明确提到，`planning-with-files` 借助 Claude Code 的 Hook 机制，在关键节点自动触发行为。

| 钩子 | 触发时机 | 作用 |
|---|---|---|
| `SessionStart` | Claude Code 启动时 | 告知插件已就绪 |
| `PreToolUse` | 执行 `Write` / `Edit` / `Bash` 前 | 重新读取 `task_plan.md` |
| `PostToolUse` | `Write` / `Edit` 完成后 | 提醒更新进度状态 |
| `Stop` | Claude 准备停止时 | 验证所有阶段是否完成 |

其中最核心的是 `PreToolUse`：

- 每次真正动手前，先回看当前计划
- 即使上下文变长，也能持续对齐目标
- 减少“写着写着跑偏”的情况
