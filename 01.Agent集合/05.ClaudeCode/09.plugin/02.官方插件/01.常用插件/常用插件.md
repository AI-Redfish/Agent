# feature-dev

说明需求，让AI先计划后开发。

```bash
/feature-dev:feature-dev
/feature-dev:feature-dev 实现用户登录功能
/feature-dev:feature-dev 为当前页面添加搜索和筛选
/feature-dev:feature-dev 重构通知模块，先分析架构再实施

把需求写得稍微具体一点，效果会更好，比如：
/feature-dev:feature-dev 在现有项目中添加暗黑模式，先分析主题结构，再实施最小改动方案
/feature-dev:feature-dev 给这个静态页面增加笔记新增、删除和本地持久化，保持现有视觉风格
/feature-dev:feature-dev 为项目增加登录态校验，先梳理相关文件和数据流
```



## 补充说明

**使用场景**

  - 新增一个完整功能
  - 改造已有功能流程
  - 需要先摸清代码结构再动手
  - 涉及前后端、状态管理、接口、组件协作
  - 想让 Claude 先分析再实施，而不是直接盲改

  

**不适用场景**

  - 改一个文案
  - 修一个很小的样式问题
  - 单行 bugfix
  - 明确到只需要改 1 个函数的简单任务





 **和直接让 Claude 改代码的区别**

  - 直接提要求：Claude 可能马上开始搜文件、改代码
  - 用 feature-dev：更偏“先理解 → 再设计 → 再实现”的节奏

/frontend-design:frontend-design 优化当前 Vue3 页面视觉层级，保留现有 data-testid

# code-simplifier

它通常用于“写完一段代码后”再做一次清理：去重复、提可读性、统一风格、尽量不改功能。



**使用方式**

```text
/simplify
/simplify 只优化最近的改动，不要改功能
/simplify 只看最近 git diff 的内容
```



# pr-review-toolkit

```
/pr-review-toolkit:review-pr
/pr-review-toolkit:review-pr 审查方面
```



## 补充说明

审查当前 PR 或当前分支改动，不是只看格式，而是从多个维度找问题。

  - 发现潜在 bug、逻辑漏洞、静默失败风险
  - 看测试是否充分
  - 看类型设计、边界情况、可维护性问题
  - 比普通“帮我 review 一下代码”更体系化

 

它背后通常会调多个专门 agent 协作评审。



**使用步骤**

  - 先进入有代码改动的仓库
  - 切到要审的分支或 PR 对应分支
  - 执行 /pr-review-toolkit:review-pr
  - 等它输出 review 结果
  - 再继续追问：
    - “只列高优先级问题”
    - “按 bug / test / type 分类总结”
    - “先修复最严重的两个问题”







# commit-commands

commit-commands 把常见 Git 提交流程封装成插件。

作用是：少敲命令、按规范完成提交/推送/开 PR。



```
# 创建一次commit提交(包含git add .)。通常会先检查改动，再帮你生成或引导你确认 commit message
/commit-commands:commit


# 一次性执行如下操作：git commit，git push,gh pr create
# 日常开发中一般使用的是MR ,所有这个命令并不适用。
/commit-commands:commit-push-pr

# 适合本地开发久了以后，清掉远程已经不存在、但本地还留着的分支。
# 一般不使用。
/commit-commands:clean_gone：
```
