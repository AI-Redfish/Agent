# StateGraph

## 基本定义

`StateGraph` 是 LangGraph 中最常用的图类型。它围绕一个共享状态 `State` 来组织节点执行。

最小结构：

```python
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END


class State(TypedDict):
    value: str


def node_a(state: State):
    return {"value": state["value"] + " A"}


builder = StateGraph(State)
builder.add_node("node_a", node_a)
builder.add_edge(START, "node_a")
builder.add_edge("node_a", END)

graph = builder.compile()
```

`StateGraph` 的关键是：每个节点都围绕同一份 state 工作。

## 编译与运行

构建图只是声明结构，真正运行前必须 `compile()`：

```python
graph = builder.compile()
```

常见运行方式：

```python
graph.invoke(input_state)
graph.stream(input_state)
graph.batch(list_of_inputs)
```

其中：

- `invoke()`：执行完整图，返回最终状态。
- `stream()`：流式查看每一步更新。
- `batch()`：批量执行多个输入。

# State

## 状态的作用

`State` 是节点之间共享的数据结构。它决定：

- 输入需要哪些字段。
- 节点可以读取哪些字段。
- 节点应该返回哪些字段的更新。
- 多个节点同时更新同一字段时如何合并。

常见写法：

```python
from typing_extensions import TypedDict


class AgentState(TypedDict):
    question: str
    answer: str
    steps: list[str]
```

## 状态设计原则

设计 state 时建议遵循：

- 字段不要太少，否则节点之间需要重复解析上下文。
- 字段不要太多，否则每个节点都难以理解。
- 把“长期稳定的信息”放在 state 中。
- 把“临时变量”留在节点内部。
- 多节点可能并发更新的字段必须考虑 reducer。

# Node

## 节点是什么

节点就是普通 Python 函数。它接收当前 state，返回一个 state 更新字典。

```python
def classify_intent(state: AgentState):
    question = state["question"]
    intent = "search" if "查询" in question else "chat"
    return {"intent": intent}
```

节点不应该关心下一个节点是谁，除非使用 `Command`。

## 节点返回值

推荐返回“增量更新”：

```python
return {"intent": "search"}
```

不推荐在每个节点都返回完整 state：

```python
return {
    "question": state["question"],
    "answer": state["answer"],
    "intent": "search",
}
```

原因是完整返回容易覆盖其他节点更新，也会让节点代码变复杂。



## 异步节点

异步节点的核心价值在于**并发处理 I/O 密集型操作**，避免阻塞事件循环，从而缩短整体工作流耗时。

- **网络请求与 API 调用**：如调用 LLM、搜索 API 或内部微服务。
- **数据库操作**：异步查询数据库，避免阻塞其他节点。
- **文件 I/O**：异步读写文件或对象存储。
- **并行分支**：图中存在多个无依赖的分支，需要并发执行时。



**不建议使用异步节点的场景：**

- **CPU 密集型任务**：如复杂的数学计算、图像处理等，异步无法加速 CPU 运算，反而可能因上下文切换增加开销。
- **简单的同步操作**：如果节点内部没有 await 操作，使用异步定义并不会带来性能提升。



**案例-并行分支**

```
import asyncio
import operator
from typing import Annotated, TypedDict

from langgraph.graph import StateGraph, START, END


# 1. 定义状态
class State(TypedDict):
    query: str
    # 使用 Annotated 和 operator.add，让并行分支的结果可以累加
    results: Annotated[list[str], operator.add]
    summary: str


# 2. 定义异步节点函数
async def prepare(state: State):
    """准备阶段，模拟轻微异步操作"""
    print(f"[prepare] 开始处理查询: {state['query']}")
    await asyncio.sleep(0.1)
    return {}


async def fetch_user_profile(state: State):
    """异步查询用户画像（模拟 I/O 操作）"""
    print("[fetch_user_profile] 查询用户画像中...")
    await asyncio.sleep(1)  # 模拟异步 IO，例如数据库/HTTP 请求
    return {"results": [f"用户画像：{state['query']} 是高活跃用户"]}


async def fetch_order_history(state: State):
    """异步查询订单历史（模拟另一个 I/O 操作）"""
    print("[fetch_order_history] 查询订单历史中...")
    await asyncio.sleep(1.5)  # 模拟另一个异步 IO
    return {"results": [f"订单历史：{state['query']} 最近 30 天有 3 笔订单"]}


async def summarize(state: State):
    """汇总结果"""
    print("[summarize] 汇总结果中...")
    await asyncio.sleep(0.2)
    summary = "；".join(state["results"])
    return {"summary": f"最终汇总 -> {summary}"}


# 3. 构建图
builder = StateGraph(State)
builder.add_node("prepare", prepare)
builder.add_node("fetch_user_profile", fetch_user_profile)
builder.add_node("fetch_order_history", fetch_order_history)
builder.add_node("summarize", summarize)

# 4. 连接边
builder.add_edge(START, "prepare")
# fan-out: prepare 之后并行执行两个异步节点
builder.add_edge("prepare", "fetch_user_profile")
builder.add_edge("prepare", "fetch_order_history")
# fan-in: 两个分支都完成后，再进入 summarize
builder.add_edge("fetch_user_profile", "summarize")
builder.add_edge("fetch_order_history", "summarize")
builder.add_edge("summarize", END)

# 5. 编译图
graph = builder.compile()


# 6. 异步运行
async def main():
    input_state = {
        "query": "张三",
        "results": [],
    }

    print("\n=== 方式 1：流式查看执行过程 ===")
    async for chunk in graph.astream(
        input_state,
        stream_mode="updates",
        version="v2",
    ):
        print("stream chunk:", chunk)

    print("\n=== 方式 2：直接获取最终结果 ===")
    result = await graph.ainvoke(input_state)
    print("final result:", result)


if __name__ == "__main__":
    asyncio.run(main())
```



**案例-同一个节点并发操作**

```
import asyncio
from typing import TypedDict

from langgraph.graph import StateGraph, START, END


class State(TypedDict):
    query: str
    sources: list[str]
    answer: str


# 三个模拟的异步 I/O 操作
async def fetch_web(query: str) -> str:
    await asyncio.sleep(1.0)  # 模拟网络请求
    return f"Web: {query} 的网页结果"


async def fetch_db(query: str) -> str:
    await asyncio.sleep(0.8)  # 模拟数据库查询
    return f"DB: {query} 的数据库结果"


async def fetch_kb(query: str) -> str:
    await asyncio.sleep(1.2)  # 模拟知识库查询
    return f"KB: {query} 的知识库结果"


# 关键：在同一个节点函数内部并发
async def multi_source_node(state: State):
    query = state["query"]

    # 并发执行三个异步任务
    results = await asyncio.gather(
        fetch_web(query),
        fetch_db(query),
        fetch_kb(query),
        return_exceptions=True,  # 某个任务失败不影响其他任务
    )

    sources = []
    for r in results:
        if isinstance(r, Exception):
            sources.append(f"失败: {r}")
        else:
            sources.append(r)

    return {"sources": sources}


async def summarize_node(state: State):
    await asyncio.sleep(0.2)
    answer = " | ".join(state["sources"])
    return {"answer": answer}


# 构建图
builder = StateGraph(State)
builder.add_node("multi_source", multi_source_node)
builder.add_node("summarize", summarize_node)

builder.add_edge(START, "multi_source")
builder.add_edge("multi_source", "summarize")
builder.add_edge("summarize", END)

graph = builder.compile()


async def main():
    result = await graph.ainvoke({"query": "LangGraph 异步节点"})
    print(result)


if __name__ == "__main__":
    asyncio.run(main())
```



# Edge

## 普通边

普通边表示固定执行顺序：

```python
builder.add_edge("node_a", "node_b")
```

执行流程：

```text
node_a -> node_b
```

从入口开始：

```python
builder.add_edge(START, "node_a")
```

到结束：

```python
builder.add_edge("node_b", END)
```

## 条件边

条件边根据 state 决定下一步：

```python
def route(state):
    if state["intent"] == "search":
        return "search"
    return "chat"

builder.add_conditional_edges("classify", route)
```

条件边适合：

- 意图识别后分流。
- 工具调用或直接回答。
- 成功/失败路径。
- 是否继续循环。

# Reducer

## 为什么需要 reducer

Reducer 是 LangGraph 学习中最容易被低估的概念。只要一个字段可能被多个节点更新，或者你希望“追加而不是覆盖”，就要考虑 reducer。

当多个节点更新同一个 state 字段时，LangGraph 需要知道如何合并。

例如消息列表通常不是覆盖，而是追加：

```text
旧 messages + 新 messages
```

如果没有 reducer，多个节点同时更新同一个 key 可能导致冲突。

## 常见 reducer

消息追加常见写法：

```python
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph.message import add_messages


class State(TypedDict):
    messages: Annotated[list, add_messages]
```

普通列表也可以使用类似追加逻辑：

```python
import operator
from typing import Annotated


class State(TypedDict):
    logs: Annotated[list[str], operator.add]
```

这表示多个节点返回的 `logs` 会合并，而不是覆盖。

# Schema

## 输入输出状态

实际项目中可以拆分输入 schema、内部 state、输出 schema。

原因：

- 外部输入不一定等于内部完整状态。
- 内部状态可能包含调试信息、工具结果、临时决策。
- 最终输出可能只暴露少数字段。

示意：

```python
class InputState(TypedDict):
    question: str


class InternalState(TypedDict):
    question: str
    intent: str
    answer: str
    tool_results: list[str]


class OutputState(TypedDict):
    answer: str
```

## 设计建议

- 学习阶段可以只用一个 state。
- 工程阶段建议区分输入、内部状态和输出。
- 对外 API 不要暴露内部调试字段。
- 内部状态字段命名要稳定，否则后续节点维护成本高。
