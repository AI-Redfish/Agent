# 项目结构

## 推荐目录

一个 LangGraph 项目可以按下面方式组织：

```text
app/
  graphs/
    main_graph.py
    agent_graph.py
    approval_graph.py
  nodes/
    classify.py
    tools.py
    summarize.py
  state/
    schemas.py
    reducers.py
  tools/
    search.py
    database.py
  memory/
    checkpointer.py
    store.py
  tests/
    test_graph.py
    test_nodes.py
```

拆分原则：

- `graphs/` 放图结构。
- `nodes/` 放节点函数。
- `state/` 放状态定义和 reducer。
- `tools/` 放工具实现。
- `memory/` 放持久化配置。
- `tests/` 放测试。

## 小项目结构

学习阶段可以简单一些：

```text
main.py
state.py
nodes.py
tools.py
```

不要一开始就过度工程化。

# 测试策略

## 测试节点

节点本质是普通函数，所以可以单独测试：

```python
def test_classify_intent():
    state = {"question": "帮我查询订单"}
    result = classify_intent(state)
    assert result["intent"] == "search_order"
```

这比每次都跑完整图更快。

## 测试图

图级测试关注整体流程：

```python
def test_graph_happy_path():
    result = graph.invoke({"question": "什么是 LangGraph？"})
    assert "answer" in result
```

复杂图建议测试：

- 正常路径。
- 条件分支。
- 工具调用路径。
- 错误路径。
- interrupt/resume。
- checkpoint 恢复。

# 调试与观测

## stream 调试

`stream()` 可以查看每一步状态变化：

```python
for event in graph.stream(input_data, config=config):
    print(event)
```

适合定位：

- 哪个节点没有执行。
- 哪个字段没有更新。
- 条件边走错了哪里。
- 工具调用是否发生。

## 状态快照

使用 checkpointer 后，可以检查图执行过程中的状态快照。

这对排查问题很有用：

- 节点执行前 state 是什么。
- 节点执行后 state 变成什么。
- 中断点保存了什么。
- resume 后是否回到了正确位置。

# 错误处理

## 工具错误

工具调用可能失败：

- 网络失败。
- 参数错误。
- 权限不足。
- 外部服务异常。
- 返回内容不符合预期。

建议：

- 工具内部捕获可预期异常。
- 返回结构化错误。
- 在 state 中记录错误。
- 让 Agent 决定重试、换工具或告知用户。

## 图执行错误

图执行常见错误：

- 状态字段缺失。
- reducer 未配置导致并发更新冲突。
- 条件边返回了不存在的节点名。
- 忘记 `compile()`。
- 使用 checkpoint 但没有传 `thread_id`。
- interrupt 后用错 config 恢复。

建议为关键节点添加最小输入校验。

# 安全实践

## 工具安全

Agent 工具要遵循最小权限：

- 不给 Agent 暴露不必要的工具。
- 高风险工具加人工审批。
- 工具参数做校验。
- 不让模型直接拼接 shell 命令或 SQL。
- 敏感操作必须记录审计日志。

## 记忆安全

记忆系统要注意：

- 不保存不必要的敏感信息。
- 用户要能删除或更新长期记忆。
- 从外部检索到的内容不能当成系统指令。
- 长期记忆进入 prompt 前要过滤和压缩。

# 配置管理

## config 的作用

LangGraph 的 `config` 常用于传入运行时配置，例如：

```python
config = {
    "configurable": {
        "thread_id": "chat-001",
        "user_id": "user-001",
    }
}
```

建议把用户 ID、会话 ID、任务 ID 等运行时信息放在 config 中，而不是硬编码到节点里。

# 生产建议

## 从简单开始

推荐演进路线：

```text
普通函数
  -> 简单 StateGraph
  -> 条件边和循环
  -> 工具调用 Agent
  -> checkpoint
  -> interrupt
  -> subgraph
  -> 多 Agent
```

不要一开始就把所有能力都加进去。

## 上线检查清单

上线前检查：

- 是否有最大循环次数。
- 是否有工具错误处理。
- 是否有稳定 `thread_id`。
- 是否使用生产级 checkpointer。
- 是否有关键路径测试。
- 是否记录必要日志。
- 是否对高风险操作加人工审批。
- 是否限制工具权限。

# 常见坑

## 把 LangGraph 当链式调用

如果只是固定顺序调用几个函数，可以不用 LangGraph。LangGraph 的价值在于状态、分支、循环、持久化和恢复。

## State 设计过大

所有东西都塞进 state 会导致节点难以维护。只把跨节点需要共享的信息放进 state。

## 缺少 reducer

并行或多节点更新同一字段时，必须考虑 reducer，否则容易出现并发更新错误。

## 没有人工确认

涉及真实副作用的操作，例如删数据、发消息、扣款、提交审批，建议使用 interrupt 加人工确认。
