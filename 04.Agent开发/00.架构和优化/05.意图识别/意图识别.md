# 为什么不能“全盘”依赖大模型？

将业务中所有请求无差别地直接转发给大模型（LLM），看似省事，实则是一种“灾难性”的设计。这种“无脑接入”的做法会从性能、成

本、可靠性三个维度引发严重危机。



## 延迟崩溃

性能灾难

- **客观限制**：大模型推理速度较慢，单次响应普遍需要 **500ms ~ 3s**。
- **后果**：高频业务请求下，累计延迟巨大，用户界面卡顿、超时，**直接劝退用户**，产品体验瞬间崩塌。



## 成本失控

财务灾难

- **计费模式**：大模型 API 按 Token 或调用次数收费。
- **后果**：一旦请求量规模化上量，简单的“转发”操作将导致**账单呈指数级增长**。原本微利的产品，可能因为模型调用费而陷入严重的成本倒挂。



## 稳定性崩塌

业务灾难

- **固有缺陷**：大模型存在**幻觉（Hallucination）**、网络**超时**、平台**限流**等不可控因素。
- **后果**：如果这些不稳定的输出直接对接核心业务逻辑（如交易、审核），一旦发生问题，**核心业务将全线瘫痪**，造成不可逆的损失与舆情危机。





# 三层架构

## 第一层：规则层 · 拦截（快速过滤）

- **定位**：系统的第一道防火墙，负责“秒级”拦截高频且表达固定的请求。

- **技术手段**：关键词匹配、正则表达式、有限状态机（FSM）。

- **响应速度**：**毫秒级（< 5ms）**，纯逻辑运算，无任何模型推理开销。

- **适用场景**：高频且意图明确的问题，例如：**「查物流」「退换货」**流程引导。

- ⚠️ **核心铁律（关键原则）**：

  > **只保留高频、明确、不变的意图，坚决避免处理「不确定的意图」**。
  > 但凡表述稍有变化（如“我的快递到哪了” vs “查下物流”），只要规则覆盖不到，就必须放过（拒绝拦截），交由下一层处理，绝不能在此层硬匹配导致误拦。

------

##  第二层：上下文层 · 承接（流量主力）

- **定位**：系统的“腰部力量”，处理大部分日常对话，是分流压力的核心。
- **覆盖流量**：承担 **50% ~ 60%** 的日常请求，是整个系统的流量担当。
- **技术手段**：**微调小模型**（如 DistilBERT、MiniLM）+ **语义向量匹配**（Embedding + FAISS 检索）。
- **核心难点**：理解真实场景中的**省略**（如“那个呢”）与**指代**（如“然后呢”），这类短句脱离上下文毫无意义。
- **关键能力**：必须具备 **对话状态追踪（DST，Dialogue State Tracking）**。
  - *工作机制*：实时记录当前对话槽位（如：当前选中的商品、订单号），当用户说省略句时，自动从上下文中补全省略的主语和谓语，再交由小模型判断意图。

------

## 第三层：工具层 · 兜底（复杂长尾）

- **定位**：系统的“最后防线”，处理前两层搞不定的“硬骨头”。注意，此层入口极窄。
- **覆盖流量**：仅处理约 **5% ~ 10%** 的复杂长尾请求。
- **技术手段**：**大模型（LLM）+ Function Calling（工具调用）**。直接将模糊的人类自然语言意图，映射为具体的系统执行函数（如查数据库、调API）。
- **适用场景**：**多意图**（既想退货又想投诉）、**隐含意图**（“这个价格有点贵”暗示想议价或找优惠券）、**表达极其模糊**的长尾需求。
- 🛡️ **必备兜底机制（防止崩盘）**：
  1. **超时降级**：若大模型响应超过阈值（如 2s），立即熔断，返回预设的兜底话术（如“人工客服正在为您转接”），避免线程阻塞。
  2. **置信度校验**：对模型生成的最终动作进行打分，若置信度低于设定阈值（如 0.7），则拒绝执行，宁可转人工或给出模糊回答，也不乱操作（如误改订单状态）。
