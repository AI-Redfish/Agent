> 适用范围：Windows 本机个人 LLM 网关——LiteLLM（pip，`litellm[extra_proxy]`）+ pgserver（pip 内嵌 PostgreSQL），全功能（管理面：Admin UI/虚拟 key/预算/统计——当前受 Prisma Windows 兼容卡点阻塞，见「实测结论」）。两种运行方式：AgentR 外部服务托管（推荐）与手动启动。
> 依据：官方 docs.litellm.ai（routing / prod / llms.txt）与 LiteLLM 源码（proxy_server.py 的 /ui 静态挂载与 prisma_client 分支）逐条核实；抓取/核实日期 2026-11-21。版本差异以实际安装版本文档为准。

# 选型结论

需求 R1 会话粘性 / R2 会话内故障切换 / R3 故障模型对新会话隔离 / R4 恢复回池 / R5 已切换会话不回切。

| 方案 | R1 | R2 | R3(OSS免费) | R4 | R5 | 本地资源 | 外部依赖 |
| :-- | :-: | :-: | :-: | :-: | :-: | :-- | :-- |
| AgentGateway 路由级 sessionAffinity | ✓ | ✓ | ✗（对健康候选集重哈希，恢复后部分会话回切） | ✓ | ✗ | 几十 MB | 无 |
| Bifrost OSS | ✓ | ✓ | △（软：新会话首击失败再 fallback；硬摘除=Enterprise） | ✓ | ✓ | 几十 MB | 无 |
| **LiteLLM pip + pgserver**（本篇） | ✓ | ✓ | **✓（cooldowns）** | ✓ | ✓（repin_on_failover） | 数百 MB | pgserver（pip 内嵌，无独立安装） |

补充事实：LiteLLM 管理数据库仅支持 Postgres-wire 协议（Prisma），MySQL/SQLite 均不可用；官方 FAQ 确认任何 Postgres-wire 兼容库可替换。pgserver 是把原生 Postgres 二进制打包成 pip 包的方案，数据目录即普通文件夹。

# 安装（pip，两个包）

```powershell
uv venv <目录>/runtime/venv --python 3.11
uv pip install --python <目录>/runtime/venv/Scripts/python.exe "litellm[proxy,extra_proxy]" pgserver
# 一次性生成 Prisma 客户端（DB 模式必需；可用 generate.py 包装脚本，自动补 PATH 与 PYTHONUTF8）
<目录>/runtime/venv/Scripts/python.exe generate.py
```

`litellm[proxy,extra_proxy]` 两个 extras 必须同时装：proxy 提供 websockets 等运行依赖，extra_proxy 提供 Prisma；`pgserver` 提供内嵌 PostgreSQL（原生二进制，数据即普通文件夹，无独立数据库安装）。

# 运行方式一：AgentR 外部服务托管（推荐，已实现）

AgentRExternal 的 `services.json` 已注册 `litellm` 服务（与 agentgateway 并列），由 Node 外部服务管理器统一启动/停止/健康检查。

- **来源类型**：`none`（本地打包形态）——为 pip 型服务新增的类型：install 跳过下载/克隆，直接执行 prepare。
- **prepare**：`uv venv runtime/venv --python 3.11` → `uv pip install "litellm[proxy,extra_proxy]" pgserver` → `generate.py` 一次性生成 Prisma 客户端（Python 锁 3.11：pgserver 无 3.13 轮子）。
- **start**：`runtime/venv/Scripts/python.exe start.py`——start.py 先用 pgserver 在 `data/pgdata` 上启动 PostgreSQL（动态端口），把 `DATABASE_URL` 注入环境，再前台拉起 `litellm`（端口 15002）。
- **环境**：管理器注入 `PYTHONUTF8=1`（必需，见实测结论）。
- **鉴权**：`LITELLM_MASTER_KEY` / `SINOMIS_API_KEY` / `GLM_API_KEY` 均经 `${secret:*}` 从本机凭据文件 `~/.agentr/external-service-secrets.json` 注入（键在 `litellm` 名下），业务侧不落明文密钥。
- **健康检查**：`GET http://127.0.0.1:15002/health/liveliness`。
- **停止**：管理器按进程树结束（taskkill /T /F）。**实测注意**：pgserver 以脱离进程树方式启动 PG，树终止后 postgres 作为孤儿实例继续运行；get_server 会检测 postmaster.pid 并复用运行中实例（已实测），下次启动无缝接管。需彻底停止时执行 pgserver 自带 pg_ctl stop，或任务管理器结束 postgres.exe。
- **Admin UI**：`http://127.0.0.1:15002/ui/`，登录账号 `admin` / 密码 = master key。

注意（升级方式）：`source.type: none` 的 source 定义恒定，prepare 仅在首次安装执行；升级 LiteLLM/pgserver 需手动在 venv 内 `uv pip install --upgrade`，或删除服务目录 `state/installed.json` 重新触发安装。

# 运行方式二：手动启动（调试用）

```powershell
$env:LITELLM_MASTER_KEY = "sk-" + [guid]::NewGuid().ToString("N")
$env:DATABASE_URL = "postgresql://..."   # 由 pgserver 获取，或指向任一本地 Postgres

```

无 `DATABASE_URL` 时退化为无 DB 模式：路由功能齐全，Admin UI/虚拟 key/预算/统计不可用（官方确认管理数据库仅支持 Postgres-wire 协议，SQLite/MySQL 不行）。

# config.yaml（config/config.yaml）

核心思路：两个上游模型作为**同一个模型组 `smart` 的两个 deployment**，权重决定新会话分配比例；会话粘性钉住 deployment；失败触发冷却（R3）+ repin（R5）。

```yaml
model_list:
  - model_name: smart
    litellm_params:
      model: openai/gpt-6.1-sol
      api_base: https://sinoai.club/v1
      api_key: os.environ/SINOMIS_API_KEY
      weight: 2
      cooldown_time: 60
      allowed_fails: 2
      num_retries: 2
  - model_name: smart
    litellm_params:
      model: openai/glm-5.3-flash
      api_base: https://open.bigmodel.cn/api/coding/paas/v4
      api_key: os.environ/GLM_API_KEY
      weight: 1
      cooldown_time: 60
      allowed_fails: 2
      num_retries: 2

router_settings:
  routing_strategy: simple-shuffle       # affinity 兼容策略（勿用旧版 usage-based-routing）
  optional_pre_call_checks: ["session_affinity"]   # R1：会话粘性
  session_affinity_repin_on_failover: true         # R5：切换成功后钉在新 deployment
  deployment_affinity_ttl_seconds: 3600            # 会话闲置超时视为新会话

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
```

# 五条需求与配置映射

| 需求 | 实现机制 | 依赖配置 |
| :-- | :-- | :-- |
| R1 粘性 | session_affinity 钉住首次服务的 deployment | `optional_pre_call_checks: ["session_affinity"]` |
| R2 切换 | A 失败进入冷却 → 该会话请求改路由到 B | `cooldown_time` / `allowed_fails` |
| R3 新会话隔离 | 冷却期内部署整体不接新请求 | 同上（cooldowns 即硬摘除） |
| R4 恢复回池 | 冷却到期自动回池 | 同上（自动） |
| R5 不回切 | 切换成功后 pin 迁移到 B | `session_affinity_repin_on_failover: true` |
| 多 key 分摊 | 同 provider 多 key 池，per-key 失败轮换 | deployment 内多 key 或多 deployment 权重 |

**客户端义务**：同一会话的每个请求必须带 `x-litellm-session-id` 头（也自动识别 Claude Code / Codex 等编码工具的会话头）；缺失则每次请求独立选路。

# 验证步骤

```powershell
curl http://127.0.0.1:15002/v1/chat/completions `
  -H "Authorization: Bearer <master_key>" `
  -H "Content-Type: application/json" `
  -H "x-litellm-session-id: s1" `
  -d '{"model":"smart","messages":[{"role":"user","content":"hi"}]}'
```

1. **粘性**：同一 `s1` 连发两请求，日志显示命中同一 deployment。
2. **切换 + 不回切**：改错 sinomis 的 api_key 重启 → s1 请求由 glm 顶上成功；恢复 key 重启 → 新会话回到 sinomis，s1 仍在 glm。
3. **Admin UI**：浏览器开 `http://127.0.0.1:15002/ui/`，账号 `admin` / 密码 = master key，确认模型与用量可见。

# 安全

- 本机自用：绑定 `127.0.0.1` + master key。
- 开放局域网：host 改 `0.0.0.0`，master key 发给可信使用者；可加 `general_settings.allowed_ips` IP 白名单。
- master key 是管理面最高凭证（可发虚拟 key），注意保管。

# 实测结论（2026-11-21，Windows 本机）

| 验证项 | 结果 |
| :-- | :-- |
| uv venv + uv pip 安装 pgserver（Python 3.11） | ✓（Python 3.13 无 pgserver 轮子，必须锁 3.11） |
| pgserver 启动真 PostgreSQL + psql 查询 | ✓（127.0.0.1 动态端口） |
| 进程树终止能否停 PG | ✗ pgserver 以脱离进程树方式启动；孤儿实例可被 get_server 复用（已验证），需 pg_ctl stop 手动彻底停止 |
| litellm[extra_proxy] 安装、CLI 可运行 | ✓（1.110.2） |
| Prisma migrate 对 pgserver PG 应用 | ✓（233 个迁移成功） |
| Prisma 客户端 connect + DB 写（虚拟 key 生成） | ✓ 已解决：0.15.0 + `PYTHONUTF8=1` + 一次性 `prisma generate`（PATH 补 venv Scripts）；启动时 LiteLLM 的 is_connected() 探测会报 `__engine` 警告——非致命（prisma-client-py 0.15 内部读法差异），实际 DB 读写正常 |
| 无 DB 模式路由功能 | ✓（前序分析，不受卡点影响） |

结论：路由五条需求与 DB 管理面（Admin UI/虚拟 key）在 Windows pip 原生环境均已实测打通；Prisma 引擎/客户端由 pip 包内嵌生成，无独立数据库安装。
