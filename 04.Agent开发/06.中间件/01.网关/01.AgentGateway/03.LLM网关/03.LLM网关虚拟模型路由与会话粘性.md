# 能力对照

| 需求 | 是否支持 | 方式 |
| :-- | :-- | :-- |
| 多模型对外暴露一个模型名 | 支持 | `llm.virtualModels[]` + 底层模型 `visibility: internal` |
| 按流量配比路由 | 支持（有限制） | `routing.weighted` |
| 上游不可用自动切换 | 支持 | `routing.failover` + 驱逐（见下） |
| 按请求内容/调用方确定性分流 | 支持 | `routing.conditional`（见「条件路由」） |
| 同一会话固定同一模型 | weighted / failover 都不支持 | 见「会话粘性替代方案」 |

# 按权重路由（weighted）

```yaml
llm:
  virtualModels:
  - name: auto
    routing:
      weighted:
        targets:
        - model: sinomis/gpt-6.1-sol
          weight: 3
        - model: glm/glm-5.3-flash
          weight: 1
```

**行为与限制**

- 逐请求随机加权选择（`choose_weighted`）。同一个会话的每次请求独立随机，按权重比例分散，**不固定模型**。
- **无健康感知**：选中不可用模型时该请求直接失败，不会自动换到其他 target。
- 模型级 `llm.models[].health` 救不了 weighted：health 驱逐只作用于该模型内部 endpoint，被 weighted 选中后照样失败。

# 故障切换（failover）

```yaml
llm:
  virtualModels:
  - name: auto
    routing:
      failover:
        targets:
        - model: sinomis/gpt-6.1-sol
          priority: 0
        - model: glm/glm-5.3-flash
          priority: 0
        - model: backup-model
          priority: 1
```

**行为**

- priority 数值小的组优先。同组内按「健康分（EWMA）+ 延迟惩罚」综合评分选最优 provider。
- 整组降级时自动切到下一 priority 组。

**驱逐（eviction）启用条件，二者满足其一**

| 方式 | 效果 |
| :-- | :-- |
| 每个模型显式配 `health.eviction`（如 `consecutiveFailures: 3`） | 连续失败后驱逐，驱逐期内不接请求；基础驱逐时间默认 3 秒 |
| targets 含 ≥2 个 priority 组 | 多优先级组自动启用默认 eviction，无需显式配置 |

- 同一 priority 组且无任何 health 配置：只有软降权，**驱逐不启用**，失败模型仍持续分到流量。
- 默认不健康判定：5xx、gRPC 服务端错误、连接失败；`unhealthyExpression` 可自定义。

**为什么无驱逐时坏模型仍接到流量（软降权 vs 驱逐）**

- 健康评分永远存在：失败扣分、成功加分，选择偏向高分者；但分低只是「被选中概率变小」，仍在候选名单里。
- 组内选择是「随机抽 2 个、取分高者」，且源码**故意允许两次抽到同一个**（注释：避免最差 endpoint 拿到 0 流量）。坏模型分数再低也会被周期性选中，每次被选中 = 一笔用户请求失败。
- 驱逐 = 把坏模型整体移出候选名单一段时间，期间被选中概率严格为 0。要让坏模型真正不被请求，必须启用驱逐。

**驱逐字段（`llm.models[].health.eviction`，schema 验证）**

| 字段 | 作用 |
| :-- | :-- |
| `duration` | 基础驱逐时长，如 `"30s"`；不配时回退：Retry-After 头 → retry backoff → 默认 3 秒 |
| `consecutiveFailures` | 连续多少次不健康响应才触发驱逐 |
| `healthThreshold` | 健康分低于该值（0.0–1.0）即可触发驱逐 |
| `restoreHealth` | 驱逐结束回归时的健康分（如 `0.2`，渐进恢复，避免立刻满流量又失败） |

# 条件路由（conditional）

`routing` 四选一：weighted / failover / conditional / callout 互斥，同一虚拟模型必须恰好配置一个（`must specify exactly one routing strategy`）。

```yaml
llm:
  virtualModels:
  - name: smart
    routing:
      conditional:
        targets:
        - when: json(request.body).route == "code"
          model: sinomis/gpt-6.1-sol
        - when: request.headers["x-tier"] == "premium"
          model: sinomis/gpt-6.1-sol
        - model: glm/glm-5.3-flash    # 无 when = 兜底，必须在最后
```

## 字段（schema/config.md）

| 字段 | 说明 |
| :-- | :-- |
| `conditional.targets` | 按数组顺序逐请求求值，首个条件为真的 target 胜出 |
| `targets[].when` | 请求期 CEL 表达式，为真才选中；省略即兜底。兜底可选，但存在时必须在最后 |
| `targets[].model` | 具体模型名（支持通配符匹配 `llm.models`：`*`、`前缀*`、`*后缀`），或嵌套另一个虚拟模型名 |

## 求值行为（逐请求，model_router.rs）

- 顺序求值，首个为真者胜出；无 `when` 的 target 恒为真。
- CEL 求值失败按 false 处理（如 body 非 JSON、字段缺失），继续匹配后续规则（`eval_bool` 出错返回 false）。
- 全部不匹配且无兜底：400，错误码 `virtual_model_no_matching_target`。
- 运行期选中的 target 解析失败：404 `virtual_model_target_not_found`，**不回落**到后续 target（官方测试 `conditional_virtual_model_invalid_match_does_not_fall_through`）。
- 无健康感知：目标不可用不换目标、请求直接失败（与 weighted 相同）；要故障切换用 failover，策略间不能叠加。

## 目标类型

- 具体模型或通配符匹配 `llm.models`。
- 可嵌套虚拟模型：target 为另一虚拟模型名时继续解析直到具体模型；配置期做环检测，运行期深度上限 4（`MAX_VIRTUAL_MODEL_DEPTH`），超限 404 `virtual_model_not_resolved`。failover 做不到（targets 必须具体模型）。
- 可选 `visibility: internal` 的内部模型：条件路由走内部 llm:router 通道，internal 目标不对外暴露但可被规则选中（官方测试验证）。
- 目标模型自身的 `authorization` 规则在条件路由后仍然生效（官方测试 `test_llm_conditional_virtual_model_allows_authorized_internal_target`）。

## 配置校验（保存/启动时，local.rs）

| 规则 | 错误信息（原样） |
| :-- | :-- |
| routing 必须恰好一种 | `virtual model X must specify exactly one routing strategy` |
| targets 非空 | `virtual model X must specify at least one conditional target` |
| 无 when 的 target 必须最后 | `virtual model X conditional fallback target must be last` |
| target 必须匹配 llm.models 或嵌套虚拟模型 | `virtual model target Y does not match any llm.models entry` |

校验顺序：先查 target 是否可解析，再编译 CEL 表达式（官方测试覆盖）。全条件无兜底的配置合法，代价是可能运行期 400。

## when 可用的 CEL

与策略同一套请求期上下文：

- `request.*`：method、path、query、headers、body 等原始 HTTP 请求字段。
- `llmRequest.*`：客户端原始 LLM 请求体 JSON 字段（如 `llmRequest.max_tokens`、`llmRequest.model`）。
- `json()`：把字符串解析为 CEL map，如 `json(request.body).route`；解析结果按请求缓存（`ParsedJson`），同一请求只解析一次。LLM 请求体在路由前已读取，可直接用。
- 常用示例：`json(request.body).route == "default"`（UI 默认占位）、`llmRequest.max_tokens <= 1024`、`request.headers["x-user"] == "admin"`。

## UI 入口

Models 页 → Add virtual model → Routing strategy 选 Conditional。每个 target 一张卡片：有条件显示 Rule N，无条件的显示 Fallback；卡片内为 CONDITION（CEL 编辑器）+ Target model 下拉（可选其他虚拟模型）。按钮 Add rule / Add fallback。Add rule 可多次点击；Add fallback 的实现是清掉现有 Fallback 再把新的追加到末尾，即 Fallback 至多一个（多个无条件 target 的配置会被校验拒绝：第一个必然不在最后）。非最后的空条件卡片触发警告 "Only the final conditional target can omit a condition."。UI 与 config.yaml 同一份数据，保存即热加载。

## 与 Failover 组合（条件选入口 + 失败切出口）

conditional 与 failover 策略互斥，但可通过嵌套组合：conditional 的 target 指向一个 failover 类型虚拟模型，实现按条件选入口、入口内失败自动切换。

```yaml
virtualModels:
- name: smart                      # 条件入口
  routing:
    conditional:
      targets:
      - when: json(request.body).route == "code"
        model: code-failover       # 嵌套指向下方虚拟模型
      - model: glm/glm-5.3-flash   # 兜底
- name: code-failover              # 失败切换出口
  routing:
    failover:
      targets:
      - model: sinomis/gpt-6.1-sol
        priority: 0
      - model: glm/glm-5.3-flash
        priority: 1
```

嵌套机制已源码验证（深度 ≤4、环检测）；该组合的实际运行行为未实测，启用前先手动停掉 priority 0 上游验证一次。

## 适用与限制

- Fallback 语义：只是「条件兜底」（所有 Rule 不命中时的默认出口），不是「模型挂掉时的备胎」。命中 Rule 但目标不可用 → 请求直接失败，不会转 Fallback。
- 伪会话粘性前提：客户端每个请求携带稳定标识（如 body 的 route/session_tier 字段或固定 header）。conditional 完全无状态：某请求落到 Fallback 后，同会话后续请求只要重新命中 Rule 就会回到 Rule 的 target。
- 适用：按请求内容/调用方做确定性分流；伪会话粘性（见下方方案 2）。
- 不适用：流量配比（weighted）、健康切换（failover）、外部动态决策（callout）。无粘性、无健康切换、无灰度比例；需要失败切换见上方「与 Failover 组合」。

# 关键限制

1. 全部 routing 策略互斥（weighted / failover / conditional / callout 四选一），不能同时配置。
2. failover 的 targets 必须是具体模型，不能嵌套虚拟模型。
3. `sessionAffinity` 挂不到 LLM 虚拟模型路由：简单配置下 LLM 路由 policy 白名单仅 guardrails / 限流 / 超时 / gateway 策略。引擎侧 `affinity_key` 通道已在 `httpproxy` 的 AI 分支实现，只差配置面接线。

# 会话粘性替代方案

按推荐排序：

1. **路由级 AI 后端 + `policies.sessionAffinity`**（粘性 + 故障切换兼得）。不用 virtualModels，普通路由挂 `backends.ai.groups`，provider 用 `provider.openAI.model` 重写模型名，配 `sessionAffinity.source`（CEL 取会话标识）。引擎按一致性哈希（rendezvous hash）粘住同一 provider，且亲和不覆盖健康与优先级。限制：流量近似等分，不能任意配比；路由级 provider 不携带 apiKey/baseUrl（见「未验证项」）。

   挂载点（schema 验证，三处，推荐第一处——亲和覆盖后端内全部 provider 与优先级组）：

   ```yaml
   binds[].listeners[].routes[].backends[].ai.policies.sessionAffinity.source
   binds[].listeners[].routes[].backends[].ai.groups[].providers[].policies.sessionAffinity
   binds[].listeners[].routes[].backends[].policies.sessionAffinity
   ```

   `source` 官方示例：`request.headers["x-session-id"]`、`string(source.address)`。

2. **conditional 伪粘性**（`llm` 段原生支持，当前配置可直接加）。按 CEL 条件把请求固定映射到指定模型：

   ```yaml
   llm:
     virtualModels:
     - name: auto
       routing:
         conditional:
           targets:
           - when: json(request.body).route == "reason"
             model: sinomis/gpt-6.1-sol
           - model: glm/glm-5.3-flash    # 无 when 的是兜底，必须在最后（源码强制校验）
   ```

   字段、求值行为与校验规则详见上方「条件路由（conditional）」。限制：映射固定，无健康切换。
3. **callout + cache（key = 会话 ID）**：官方 schema 明确支持的真正粘性，需要外部决策服务。
4. **改造源码**：把 SessionAffinity 接入 LLM 虚拟模型路由。

# 配置入口（UI 与文件）

UI 与 config.yaml 是同一份数据，UI 改动保存即热加载生效。

| 配置 | UI 菜单 | 说明 |
| :-- | :-- | :-- |
| 驱逐（eviction） | Models 页 → 选择模型 → Health policy 编辑器 | 有表单 |
| 会话亲和（sessionAffinity） | 无 UI 表单 | 只能 UI 的 Raw Config 页或直接改 config.yaml |

Health policy 编辑器字段与 config.yaml 对应：Unhealthy expression → `health.unhealthyExpression`；Eviction duration → `health.eviction.duration`；Consecutive failures → `health.eviction.consecutiveFailures`；Health threshold → `health.eviction.healthThreshold`；Restore health → `health.eviction.restoreHealth`。
